# Xenon 完整审查报告（2026-07-27）

## 结论摘要

Xenon 当前不应被判定为“通用任务正确率只有 45%”。现有 45% 和 55% 两次真实跑测是评测框架的工具闭环代理分数，不是端到端正确率；它们不能直接代表日常使用成功率，也不能与用户实际体验作一一对应。

目前更可靠的判断是：

| 维度 | 结论 | 证据强度 |
| --- | --- | --- |
| 离线工程回归 | 稳定 | 高：GitHub CI 最新运行全绿，Python 3.10/3.11/3.12、Ubuntu/macOS/Windows、打包均通过 |
| 工具安全与边界 | 有较完整的工程防线 | 中高：大量单元/集成测试，评测中观察到参数与路径拦截 |
| 日常交互可用性 | 与用户反馈一致，基本可用 | 中：有真实 REPL/e2e 测试，但不是统计学用户研究 |
| LLM 任务端到端正确率 | 尚未测准 | 低：任务夹具、评分和断言仍不完整 |
| Cache Rails/成本收益 | 有真实供应商证据 | 中高：一次 20 任务跑测命中率 85.98%，估算节省 79.77% |

因此当前产品方向应保持为：**正确性优先，效率放大**。下一阶段不是继续堆缓存优化，而是建立可信的任务正确性闭环；缓存、路由和 Token 优化必须在正确结果成立后再比较。

## 2. 为什么 45%/55% 不能当作真实正确率

### 2.1 评分实际测的是“工具调用覆盖”

当前基础评分要求：

```text
expected_tools ⊆ executed_tools 且 final_answer 非空
```

这能回答“模型是否走过预期工具路径”，但不能回答：

- 文件是否修改成了目标状态；
- 修改是否破坏已有行为；
- 测试是否真的通过；
- 搜索结论是否与代码事实一致；
- MCP/记忆/会话操作是否产生了预期持久化结果。

`success_criteria` 目前只是报告中的人工复核提示，不参与自动评分。20 个任务中只有 7 个配置了断言，而且当前两次真实跑测均早于断言框架提交。

### 2.2 任务夹具与任务前提不一致

两次跑测使用了不同工作目录：

- 55% 跑测的夹具包含一个最小 greeter 项目，任务却大量要求修改 Xenon 的 `src/main.py`、查找 provider 路由和项目上下文。
- 45% 跑测的隔离目录同样主要是 `src/main.py`/`tests/test_main.py`，不是 Xenon 源码树；因此代码搜索和编辑任务的失败有相当部分是测试环境制造的。
- 任务本身要求 `src/main.py`，而 Xenon 的实际 CLI 入口是 `xenon/main.py` 和 `pyproject.toml` 中的 `xenon.main:cli`。

这会同时造成两类偏差：模型因为找不到前置材料被低估；模型为了完成空夹具任务自行创建文件，又可能被高估为“完成”。

### 2.3 工具调用并不等于工具成功

`RealAgent` 的 `_execute_tool` 包装器在调用原始执行函数之前就把 action 放入 `executed` 列表。也就是说，工具返回 `success=False`、路径不存在、参数错误或权限拒绝时，仍可能满足 `expected_tools ⊆ executed_tools`。

报告中的 `tool_failures` 目前主要表示“缺少预期工具”，不是工具返回失败的次数。因此基础成功率存在高估风险；而夹具错配又造成低估风险，二者方向相反，不能靠一个百分比抵消。

### 2.4 结果断言仍处于早期阶段

当前断言支持文件存在、文件内容、回答包含/不包含等检查，这是正确方向，但已有任务多数只使用 `answer_contains_any`。例如回答中提到 `provider_registry` 只能证明模型说到了这个词，不能证明它真正定位并正确解释了路由实现。

后续必须优先使用机器状态断言：文件差异、AST/函数签名、测试退出码、命令副作用、MCP 注册表状态、记忆条目和会话恢复后的上下文变量。

## 3. 两次真实跑测的正确解读

### 3.1 45% 跑测（metrics-r3）

- 20 个任务，9 个基础成功。
- CacheTracker 字段覆盖率 100%。
- Cache Rails 命中率 85.98%。
- 可复用前缀命中 1,416,064 tokens。
- 估算实际费用 ¥1.0684；全 cache-miss 基线 ¥5.2812；预计节省 ¥4.2128（79.77%）。
- 观察到 2 次参数拦截、2 次路径越界拦截、1 次 rail 分叉。

这次跑测对缓存遥测很有价值，但对通用正确率的价值有限，因为工作目录不是 Xenon 的真实项目夹具，且没有使用最新结果断言。

### 3.2 55% 跑测（full-source fixture）

- 20 个任务，11 个基础成功。
- 使用了更接近 Xenon 的完整源码/文档夹具，代码搜索结果明显比最小 greeter 夹具合理。
- 仍有 `src/main.py` 路径错配、需要 REPL 命令的任务无法由纯 ReAct runner 完整执行、以及部分回答声称完成但没有可验证副作用等问题。

这次结果说明“环境质量会显著改变分数”，不能把 55% 解释为 Xenon 的上限，也不能把 45% 解释为 Xenon 的下限。

## 4. 当前工程健康度

### 已验证的强项

1. **回归稳定性**：最新 GitHub Actions CI（`99abf42`）成功完成 3 个 Python 版本的离线测试与覆盖率门槛、3 个操作系统的平台 smoke、确定性 CLI e2e，以及 wheel/sdist 构建和 twine 校验。
2. **核心防线**：工具执行管线包含参数规范化、幻觉检测、权限闸门、断路器、超时和结构化结果；路径边界、权限、取消和错误分类均有测试覆盖。
3. **产品闭环**：Cache Rails、费用展示、模型路由、记忆作用域、MCP/Skills、会话保存/恢复和终端界面均已有实现与对应测试。
4. **缓存证据**：当前缓存指标取自供应商 usage 字段，并与 UsageTracker 分离，避免把本地估算冒充厂商命中。

### 仍需谨慎的部分

1. **真实 LLM 任务质量未知**：离线单测证明代码路径稳定，不等价于模型在开放任务上的正确率。
2. **REPL 与 ReAct 评测脱节**：`/mcp`、`/compact`、`/memory`、`/resume` 等用户日常路径不能只通过裸 ReAct 工具循环评测。
3. **记忆/恢复遥测未接入该评测**：报告显示 `N/A`，这不是零分，而是尚未观测。
4. **PyPI 发布链路仍有历史失败记录**：GitHub Release v0.7.3 本身已有 wheel/sdist 资产，但 `Publish to PyPI` 工作流历史运行失败；发布链路需单独修复并复验。

## 5. 对“日常使用已经足够”的判断

用户的日常体验与低分并不矛盾，原因是两者测量对象不同：

- 日常使用通常是熟悉的项目、连续上下文、明确的文件结构、用户可即时纠偏的交互任务；
- 当前 20 任务集是合成的、一次性的、工具列表驱动的任务，且部分任务没有正确 fixture；
- 用户会在模型第一次偏离时补充信息，评测 runner 则把每个任务拆成固定脚本；
- Xenon 的价值还包括权限可控、可恢复、缓存节省和透明观测，这些不能压缩成一个“答对/答错”数字。

所以目前最诚实的产品结论是：**Xenon 的日常可用性已有实际依据，但通用任务成功率尚未被严谨量化。** 不能宣传 45%，也不能未经新评测宣传 90% 或“全任务正确”。

## 6. 下一轮可信验收方案

### P0：先修评测，不改缓存

1. 为每个任务建立独立、最小且真实的 fixture；任务 prompt 中的路径必须与 fixture 一致。
2. 将任务拆成文件编辑、代码搜索、工具执行、REPL/记忆/会话、多轮修订五个套件。
3. 记录工具返回的 `ToolExecuteResult.success/state/error`，只有成功执行才计入工具覆盖。
4. 为 20/20 任务配置结果断言；优先文件状态、测试退出码、注册表/会话/记忆状态，最后才使用回答关键词。
5. 把 ReAct runner 与真实 REPL 命令路径分开评测，不能用“不支持 REPL”判定引擎能力。

### P1：建立用户相关性

1. 从 Xenon 自己的真实工作流抽取 10～20 个脱敏任务，保留基线文件和预期 diff。
2. 每个任务至少重复 3 次，报告 pass@1、pass@3、验证成功率和人工复核结果。
3. 对 direct、ReAct、Plan-Execute 做同任务 A/B；固定模型、提示词、fixture 和预算。
4. 把“正确结果”与“效率”分层展示：只有 verified success 的任务才进入 tokens/cost per successful task。

### P2：再做效率优化

当 verified success rate 稳定后，再比较 Cache Rails、模型路由和上下文压缩；优化目标是“同等正确结果下更少 Token/费用”，而不是用缓存节省掩盖错误。

## 最终审查结论

Xenon 目前更像一个已经具备稳定工程底座、日常可用、效率特色明确，但 LLM 端到端基准仍不成熟的 Beta 产品。当前最重要的工作不是推翻架构或继续堆功能，而是把真实用户任务转化为可重复、可验证的验收闭环。
