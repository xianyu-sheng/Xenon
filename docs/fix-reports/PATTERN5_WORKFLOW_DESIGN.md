# Pattern 5 修复工作流设计

## 概述

这是一个完全自动化的多Agent协作工作流，用于修复 Pattern 5 的并发安全问题。工作流包含6个阶段，每个阶段由专门的Agent负责。

## 工作流架构

```
┌─────────────┐
│   分析器    │ → 理解问题，生成修复计划
└──────┬──────┘
       ↓
┌─────────────┐
│   实现者    │ → 编写修复代码
└──────┬──────┘
       ↓
┌─────────────┐
│   审查者    │ → 代码审查，确保质量
└──────┬──────┘
       ↓
┌─────────────┐
│   测试者    │ → 运行测试验证
└──────┬──────┘
       ↓
┌─────────────┐
│   提交者    │ → 提交代码，创建PR
└──────┬──────┘
       ↓
┌─────────────┐
│   监控者    │ → 监控CI，处理失败
└─────────────┘
```

## 阶段详解

### Phase 1: 分析 (分析器)
**职责**: 理解问题和测试要求
**输入**: tests/test_pattern5_concurrency.py
**输出**: 结构化的问题分析
- 每个问题的ID、标题、当前/期望行为
- 需要修改的文件列表
- 复杂度评估

**Schema**: `ANALYSIS_SCHEMA` - 确保输出结构化

### Phase 2: 实现 (实现者)
**职责**: 编写修复代码
**输入**: 分析结果
**输出**: 修改后的源文件
**要求**:
- 每个修改都有注释说明修复的问题
- 保持代码风格一致
- 确保线程安全

**Schema**: `IMPLEMENTATION_SCHEMA` - 跟踪修改的文件和成功状态

### Phase 3: 审查 (审查者)
**职责**: 代码审查和质量检查
**输入**: 修改后的文件
**输出**: 审查结果和问题列表
**检查点**:
1. 线程安全（锁的使用）
2. 边界条件（百分比范围）
3. 错误处理
4. 代码质量
5. 性能影响
6. 向后兼容

**严重等级**:
- `critical`: 必须修复，阻止合并
- `major`: 应该修复
- `minor`: 可选改进

**Schema**: `REVIEW_SCHEMA` - 包含批准状态和问题列表

### Phase 4: 测试 (测试者)
**职责**: 运行测试验证修复
**输入**: 修改后的代码
**输出**: 测试结果
**测试范围**:
1. Pattern 5 专项测试
2. 相关模块测试（repl, status_bar）

**失败处理**: 收集错误日志，准备回滚

**Schema**: `TEST_SCHEMA` - 详细的测试通过/失败统计

### Phase 5: 提交 (提交者)
**职责**: 提交代码并创建PR
**步骤**:
1. 创建新分支 `fix/pattern5-concurrency`
2. 提交修改
3. 推送到远程
4. 创建PR（带详细描述）

**提交信息格式**:
```
fix: Pattern 5 并发安全问题修复

修复 Pattern 5 中发现的 4 个并发安全问题:
- 问题1: StatusBar.refresh() 回调机制
- 问题2: StatusBar._parse_pct() 百分比解析
- 问题3: ContextManager 线程安全
- 问题4: 进度条超限保护

Co-Authored-By: Claude <noreply@anthropic.com>
```

**Schema**: `COMMIT_SCHEMA` - 包含分支、提交哈希、PR号

### Phase 6: 监控 (监控者)
**职责**: 监控CI状态并处理失败
**监控策略**:
- 等待CI开始（最多2分钟）
- 轮询检查（每30秒，最多10分钟）
- 收集失败日志

**失败处理**:
1. 分析失败原因
2. 决定是否回滚
3. 如果需要回滚：
   - 删除本地和远程分支
   - 关闭PR
   - 返回失败日志用于调试

**Schema**: `MONITOR_SCHEMA` - CI状态和检查结果

## 错误处理

### 分阶段失败
每个阶段失败都会抛出异常，包含详细的错误信息：
- 分析失败 → 无法理解问题
- 实现失败 → 代码修改错误
- 审查失败 → 存在严重问题
- 测试失败 → 功能不正确
- 提交失败 → Git/GitHub操作失败
- 监控失败 → CI失败

### 自动回滚
当CI失败且 `needs_rollback=true` 时，自动执行回滚：
1. 切换回main分支
2. 删除失败的分支（本地+远程）
3. 关闭PR并添加失败说明
4. 保留失败日志供分析

## 使用方法

### 运行工作流
```javascript
Workflow({
  scriptPath: '/home/xianyu-sheng/Xenon/workflows/pattern5_fix.js'
})
```

### 查看实时进度
```
/workflows
```

### 迭代修复（如果首次失败）
1. 编辑工作流脚本修复问题
2. 使用 resumeFromRunId 恢复：
```javascript
Workflow({
  scriptPath: '/home/xianyu-sheng/Xenon/workflows/pattern5_fix.js',
  resumeFromRunId: 'wf_xxx'
})
```

## 优势

### 1. 完全自动化
从分析到CI监控，无需人工干预

### 2. 结构化输出
使用JSON Schema确保每个Agent的输出格式一致

### 3. 质量保证
- 代码审查阶段捕获问题
- 测试阶段验证功能
- CI监控确保无回归

### 4. 可恢复性
- 失败时自动回滚
- 保留失败日志供调试
- 支持从任意阶段恢复

### 5. 可追溯性
- 每个阶段的输出都被记录
- 清晰的决策链
- 完整的修复历史

## 输出格式

工作流最终返回完整的执行记录：
```json
{
  "phase": "completed",
  "analysis": { ... },
  "implementation": { ... },
  "review": { ... },
  "testResults": { ... },
  "commit": { ... },
  "monitor": { ... },
  "summary": "Pattern 5 并发安全问题修复成功"
}
```

## 监控

使用 `/workflows` 命令实时查看工作流进度：
- 当前运行的阶段
- 各Agent的状态
- 实时日志输出

## 注意事项

1. **模型选择**: 所有Agent使用 `claude-sonnet-4-20250514` 确保一致性
2. **超时设置**: CI监控最多等待10分钟
3. **权限要求**: 需要Git和GitHub CLI权限
4. **分支命名**: 固定使用 `fix/pattern5-concurrency`

## 扩展性

这个工作流模式可以复制用于其他Pattern的修复：
- 修改 `meta.name` 和 `meta.description`
- 调整测试文件路径
- 更新问题描述
- 保持相同的6阶段结构
