# v0.8.3 方向思考：引擎层跨轮次验证循环（公共组件，7 引擎统一接入）

> 目的：论证 v0.8.3 核心改动——把 v0.8.2 的 Plan-Execute 单机验证闭环
> 提升为**引擎层公共组件**（`verification_loop.py`），7 种推理范式统一接入
> 学习式多轮验证循环（失败时间线 + 成功缓存一体）。不做 Plan-Execute 专用
> 的阉割版——要做就做统一的。
> 目标：SWE-bench_Lite 45-50% instance-level（当前 v0.8.2 = 40.0%）。
> 版本：v0.8.3（引擎层架构升级；框架级范式变化留给 v0.9）。

---

## 1. 背景与动机

### 1.1 已验证的因果链

v0.8.2 的核心提升来自 **Plan-Execute 引擎的验证闭环**：把「写了文件但
测试失败且无成功测试」转成一轮修复执行。同模型 A/B 实证 **+6.7pp instance
/+11.0pp cell**。

但验证闭环只挂在 Plan-Execute 一个引擎上。v0.8.2 每引擎 resolved 数据：

| 引擎 | resolved | 有无验证闭环 |
|------|----------|------------|
| ReAct | 9 | ❌ |
| Reflection | 7 | ❌ |
| Plan-Execute | 2 | ✅（单轮） |
| Plan-React | 8 | ❌ |
| React-Reflection | 7 | ❌ |

**ReAct 系引擎（react 9 + plan-react 8 + react-reflection 7 = 24）解决
了 24/33 = 73% 的实例，但它们全都没有验证闭环。** 如果验证闭环提升到
引擎层，收益面是 7 引擎而不是 1 引擎。

### 1.2 v0.8.2 的三个缺口（跨引擎视角）

1. **单轮终止**：验证闭环只在 Plan-Execute 里，且只修一次不复查；
2. **无跨轮状态传递**：各引擎、各轮次之间没有失败/成功信息的累积；
3. **无复用**：已验证正确的动作不被缓存，后续重做浪费成本。

缺口 2、3 是同一机制的两面——**跨轮次确定性验证状态传递**。这个机制
与引擎无关：ReAct 的循环、Reflection 的反思步骤、Plan-Execute 的计划
步骤，底层都是「执行→验证→判断是否继续」的循环，都可以接入同一个
验证组件。

## 2. 架构设计：引擎层公共验证组件

### 2.1 组件定位

```
BaseEngine
  ├── execution loop（各引擎自实现）
  ├── EvidenceGate（已有，零-LLM 校验）
  ├── HollowDetector（已有，空洞回答检测）
  └── VerificationLoop（新增，引擎层公共组件） ← NEW
         ├── 跨轮次验证循环
         ├── 失败时间线累积
         ├── 成功缓存 + 证据 ID
         └── 动态终止策略
```

`VerificationLoop` 是 `BaseEngine` 的**可选拦截器**——引擎在每一步执行
后调用 `VerificationLoop.feed(execution_evidence)`，组件自动判断：
- 是否需要进入验证循环（有写操作 + 有失败测试 + 无成功测试）；
- 循环内是否继续（失败时间线有进展 → 继续；绕圈 → 终止）；
- 哪些证据可复用（确定性验证通过的测试/写入 → 缓存注入下一轮）。

### 2.2 跨轮次状态传递（核心机制）

```
执行 → 测试 → 捕获 ExecutionEvidence
                  │
           ┌──────┴──────┐
           ▼              ▼
     失败证据         成功证据
   (错误时间线)     (复用缓存)
           │              │
           └──────┬───────┘
                  ▼
        累积注入下一轮/引擎 prompt
```

**失败时间线（错误日志累积）：**
- 每轮把失败测试输出做结构化摘要后追加到时间线（提取「失败类型 + 关键
  断言/错误行 + 涉及文件」），而非全文覆盖；
- 第 N 轮 prompt 包含第 1..N-1 轮的全部摘要；
- 分级压缩：最近 3 轮保留原始摘要，更早压缩为一行级轨迹。

**成功缓存（正确动作复用）：**
- 每轮结束，`ExecutionEvidence` 把验证通过的证据分类标记：通过的测试
  命令、成功写入的文件、成功的工具调用 → 各自绑定证据 ID；
- 下一轮 prompt 标注「以下已确定性验证通过，无需重做」，带证据 ID 列表；
- 复用必须绑定证据 ID（框架校验真实存在且仍有效）；
- 只有确定性验证通过的才进缓存，LLM 自述「正确」但不带验证证据的
  一律不缓存（防信任幻觉）。

**证据时效语义（补缺）：**
- 证据不是永久有效。文件写入证据：该文件被后续修改 → 该写入证据失效；
- 测试命令通过证据：测试重跑且结果变化 → 旧通过证据标记为「被覆盖」；
- 最终一轮强制完整验证（复用省的是中间探索，不是最终确认）；
- 证据失效时自动从缓存中移除，下一轮 prompt 不再标注「无需重做」。

### 2.3 轮次预算与动态终止

- 上限 8-10 轮（配置化 `verification_max_rounds`）；
- 动态提前终止：
  - 无进展检测：连续 2-3 轮失败摘要相同（LLM 在绕圈）→ fail-closed；
  - 收敛检测：失败摘要逐轮变化且在变短 → 继续给轮次；
  - 双闸门：仍受 `max_steps` 总预算约束。

### 2.4 各引擎接入方式

| 引擎 | 接入点 | 说明 |
|------|--------|------|
| ReAct | `run()` 循环尾部 | 每一步工具调用后检查是否需要进入验证循环 |
| Plan-Execute | `_ensure_verification_loop` 替换为组件 | 现有单轮升级为多轮 |
| Reflection | `_execute()` 反思后 | 反思结论先过验证再决定是否继续 |
| Combined | 各子引擎执行后 | 引擎切换时状态不丢失（验证组件跨引擎持久化） |

不需要每引擎单独实现——组件在 `BaseEngine` 层注册，各引擎只需在
执行循环尾部调用 `self.verification_loop.feed(evidence)` 即可。

## 3. 与模型侧思考档的关系（正交杠杆）

`reasoning_effort` 控制单次推理深度，与框架侧迭代策略正交：
- 当前代码默认 `deepseek-v4-pro → max`，flash 未设档；
- v0.8.3 B 组对 flash 开 max 验证独立收益；
- 两个杠杆叠加 = 每轮修复质量更高（模型侧）× 轮数更多且有学习
  （框架侧）= 联合增益。

## 4. 预期收益与成本边界

### 4.1 收益估算（按引擎分组）

| 来源 | 机制 | 引擎 | 预期 |
|------|------|------|------|
| 跨轮次状态传递 | 失败时间线 + 成功缓存 | Plan-Execute | +2-3pp（现有闭环升级） |
| 同上 | 同上 | ReAct / Plan-React / React-Reflection | **+3-5pp**（从零到有，面最大） |
| 同上 | 同上 | Reflection | +1-2pp（反思引擎本身有自我修正，但缺验证反馈） |
| max 档（flash） | 单次推理深度 | 全部 | +1-3pp |
| **叠加** | 正交杠杆联合 | 全部 | **45-50%**（目标） |

**关键逻辑**：ReAct 系引擎解决了 24/33 = 73% 的实例但全无验证闭环，
即使只提升 10-20% 也是 2-5 个实例，对应 +6-17pp——**跨引擎推广的
收益可能远超单独优化 Plan-Execute**。

### 4.2 成本边界

- 多轮 token 膨胀（×3-5）被成功复用抵消：已验证步骤不重做，复杂任务
  越到后面每轮新增成本越低；
- 纯读任务/无失败测试任务零成本（沿用触发条件）；
- 组件在引擎层，一次实现 × 7 引擎，边际成本为零。

## 5. 实验设计（唯一变量原则）

### 5.1 实验分组

1. **A 组：引擎层验证组件**（框架侧唯一变量）
   - 基线：v0.8.2（单轮闭环，仅 Plan-Execute）
   - 实验：所有引擎接入 VerificationLoop 组件（8-10 轮 + 动态终止）
   - 模型固定：flash 同档位；seed 同 20260729；`--max-steps 10`
   - **按引擎分组报告**：react / plan-execute / plan-react / reflection /
     react-reflection 各多少 resolved，验证组件增益是否跨引擎一致
2. **B 组：flash max 思考档**（模型侧唯一变量）
   - 基线：A 组基线（flash 未设档）
   - 实验：flash `reasoning_effort=max`
3. **C 组：联合**（两杠杆叠加）
4. **判定标准**：instance-level resolved 数提升 ≥ 2（≈ +6.7pp 量级）；
   按引擎拆解确认「所有引擎都有正向收益」才合入（防止总提升来自
   单一引擎的 outlier）。

### 5.2 实施步骤

1. 新建 `xenon/engine/verification_loop.py`（VerificationLoop 组件）
2. 组件实现：循环化 + 失败时间线 + 成功缓存 + 证据时效 + 动态终止
3. `BaseEngine.__init__` 注册可选组件；各引擎 `run()` 尾部调用
   `self.verification_loop.feed(evidence)`
4. Plan-Execute 现有 `_ensure_verification_loop` 迁移为组件调用
   （单轮→多轮 + 状态传递）
5. 单测（8 个用例）：
   - 补救后仍失败 → 第二轮补救且看到第一轮失败摘要
   - 第二轮成功后 → 立即退出
   - 成功证据注入后 → LLM 跳过已验证步骤
   - LLM 声称复用但不带证据 ID → 拒绝
   - 预算耗尽 → fail-closed
   - 无进展 2-3 轮 → 提前终止
   - 证据失效 → 缓存自动移除
   - 多引擎切换 → 验证状态不丢失
6. 门禁：pytest（2110+）+ ruff + compileall + 本地安装验证
7. 5 引擎 × 30 实例串行评测，结果按引擎分组入库
8. 通过则 bump 0.8.2 → **0.8.3**，双远端 + release + CI

## 6. 风险与回退

| 风险 | 应对 |
|------|------|
| 跨引擎收益不均（某引擎无效） | 组件支持按引擎开关（`verification_enabled_engines` 配置项），无效引擎关闭 |
| 失败时间线撑爆 prompt | 分级摘要 + 8-10 轮上限 + 动态终止 |
| 证据时效判断不准确 | 简化策略：每次文件修改 → 该文件所有写入证据失效；每次测试重跑 → 该测试旧通过证据标记为「待覆盖」 |
| 组件与引擎耦合过紧 | VerificationLoop 只依赖 ExecutionEvidence 和 AgentContext，不依赖引擎类型；引擎通过 `feed()` 松耦合调用 |
| 评测成本（5 引擎 × 30 实例 × 多轮） | 成功复用抵消部分膨胀；先 A 组 C 组（long run）后 B 组（short run）若 A 组增益不足则不跑 C 组 |

## 7. 面试叙事（「自己独有的方法」）

**三段论：**

1. **问题**：Agent 框架没有「验证状态跨轮次传递」——
   LangGraph/LangChain 的验证是节点级单步校验，AutoGen 的反思是
   对话级角色讨论，没有人在引擎执行循环层面做「确定性验证结果
   （成功+失败）的跨轮次累积与复用」。

2. **方案**：Xenon 在引擎层实现了 `VerificationLoop` 公共组件——
   7 种推理范式统一接入。每轮执行后 `ExecutionEvidence` 捕获验证
   结果，按成功/失败分类累积（失败时间线 + 复用缓存），注入下一轮
   prompt。证据绑定 ID 防假复用，带时效语义自动失效。

3. **实证**：SWE-bench_Lite 官方 harness 40.0% → 45-50%，按引擎
   分组报告确认所有引擎正向收益。同模型 A/B 隔离框架增益。

对比「我在 Plan-Execute 里加了多轮重试」——前者是**框架设计**，
后者是**功能补丁**。
