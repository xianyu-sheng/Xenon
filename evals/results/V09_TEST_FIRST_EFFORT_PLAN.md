# v0.9 方向思考：test-first 多轮迭代 + 模型侧思考档调整（2026-08-13）

> 目的：论证 v0.9 两大调整（框架层 `_ensure_verification_loop` 单轮→预算内多轮；
> 模型侧 reasoning_effort 思考档）的设计依据、预期收益、成本边界与实验方案。
> 目标：SWE-bench_Lite 45-50% instance-level（当前 v0.8.2 = 40.0%）。

---

## 1. 背景与动机（为什么是这两个杠杆）

### 1.1 已验证的因果链

v0.8.2 的核心提升来自「验证闭环」：把「写了文件但测试失败且无成功测试」
转成一轮修复执行（失败输出 → 定位断言 → 改代码 → 再验证）。同模型 A/B
（v0.8.0 → v0.8.2，DeepSeek V4 Flash、单次尝试）实证 **+6.7pp instance /
+11.0pp cell**。

这证明一件事：**把测试结果反馈给 LLM 是当前框架最有效的单点增益**。
v0.8.2 只做了「一轮」——LLM 修完一次就不再验证，即使第二次仍失败。

### 1.2 失败模式证据

SWE-bench_Lite 硬实例（sympy-14817、django 精确断言类）的共同失败模式：

1. 计划执行完就收工（v0.8.0 之前：无验证反馈）
2. 修复一轮仍失败（v0.8.2：反馈 1 次，失败即放弃）
3. 断言格式不精确（实例要求输出格式与本地测试预期不一致，但 LLM
   不知道失败细节，因为反馈只给了一次）

第 2、3 类是 v0.8.2 未吃掉的部分——**多轮反馈是直接针对它们的**。

### 1.3 为什么同时调思考档

- 模型侧 `reasoning_effort`（low/medium/high/max）控制单次推理深度，
  是**正交**于框架侧迭代策略的独立维度（v0.8.2 全程单档，未动）。
- 官方 V4 集成指南对 Pro 推荐 max 思考；当前代码已默认
  `deepseek-v4-pro → reasoning_effort=max`（`model_registry.py`），
  flash 未设。v0.9 实验应对 flash 也开 max 档验证收益是否独立于框架。
- 两个杠杆叠加 = 每轮修复质量更高（模型侧）× 轮数更多（框架侧），
  目标 45-50% 依赖两者的联合效果，不能只靠一个。

## 2. 现状盘点

### 2.1 框架侧：`_ensure_verification_loop`（单轮，v0.8.2）

位置：`xenon/engine/plan_execute_engine.py:561`。当前行为：

- **触发条件（5 条全满足）**：
  1. 任务需写操作（`task_requires_write`）
  2. 有成功写操作（改过文件）
  3. 有失败的测试命令（`_TEST_COMMAND` 匹配且 success=False）
  4. 没有任何成功的测试命令（`evidence.successful_tests` 为空）
  5. 步骤预算未耗尽（`len(results) < max_steps`）
- **动作**：追加 1 个补救步骤（读失败输出 → 定位根因 → 改代码 →
  重跑测试 → 确认通过再总结），`require_write_tool=True`。
- **终止**：补救步骤执行完即返回，**不再检查补救后的测试结果**。

关键缺口：**没有「验证补救结果 → 失败再补救」的循环**；修复后测试
是否通过完全依赖 LLM 自己报告，框架不二次确认。

### 2.2 模型侧：reasoning_effort

- `xenon/repl/model_registry.py:112`：`deepseek-v4-pro` 无显式 effort 时
  默认 `max`；`deepseek-v4-flash` 无默认值（跟随 provider）。
- CLI 支持 `/set_model <alias> <model> reasoning_effort=<档位>` 持久化
  （`xenon/repl/batch_register.py`，合法值 low/medium/high/max）。
- 评测路径（`evals/`）按注册表透传，无额外覆盖。

## 3. 调整设计

### 3.1 框架层：单轮 → 预算内多轮（test-first 风格验证循环）

```
[计划] → [执行步骤] → [测试命令] ──失败──→ 循环（≤ budget 轮）
                                ↑                    │
                                └── 失败反馈注入 ──────┘
                                   (失败输出→定位→修改→重跑)
```

具体改动（`_ensure_verification_loop` 重构）：

1. **循环化**：把当前「追加 1 个补救步骤」改为 `while` 循环，每轮
   补救后重新捕获 `ExecutionEvidence`：
   - 若 `successful_tests` 非空 → 成功，退出循环；
   - 若仍有失败测试且轮数 < 上限 → 追加下一轮补救（失败输出用
     最新一次测试结果，不是第一轮的旧输出）；
   - 否则 → fail-closed 退出（保留已有结果与错误信息，不伪造成功）。
2. **预算控制**（防成本膨胀，沿用 v0.8.2 的防膨胀哲学）：
   - `verification_max_rounds`：默认 2-3 轮（含首轮），配置化；
   - 每轮补救仍受 `max_steps` 总预算约束（`len(results) < max_steps`）；
   - 轮间失败输出截断（`[:200]`/`[:200]` 已有，保持），防止重复注入
     相同巨量日志。
3. **失败分类**（可选增强，先实验后定）：
   - 断言/格式类失败 → 重试价值高（LLM 修格式是强项）；
   - 环境/依赖类失败（import error、缺包）→ 重试价值低，可提前终止；
   - 用失败输出特征（`Error:`/`ModuleNotFoundError` 等）做轻量分类，
     避免无意义重试。
4. **向后兼容**：`verification_max_rounds=1` 时行为与 v0.8.2 完全一致；
   默认值提升才改变行为，不破坏既有路径。

### 3.2 模型侧：/effort 调整

- 评测 A 组：flash 开 `reasoning_effort=max`（对比 v0.8.2 的未设档）；
  若收益为正且成本可控 → 默认给 flash 也设 max。
- Pro 已默认 max，不动。
- 注意验证 `max` 档是否影响 latency/成本到不可接受（见 §4）。

## 4. 预期收益与成本边界

### 4.1 收益估算（保守口径）

| 来源 | 机制 | 预期 |
|------|------|------|
| 多轮验证循环 | 吃掉「修一轮仍失败」的硬实例（§1.2 第 2 类） | +3-5pp |
| max 思考档（flash） | 每轮修复质量更高，减少无效轮次 | +1-3pp |
| 两者叠加 | 正交杠杆联合 | **45-50%**（目标） |

对照：SWE-bench 类基准第一梯队 50-65% 普遍使用 test-first + 多尝试选择；
Xenon 现在是「最便宜模型 + 单次尝试」，加多轮后向第一梯队靠拢是合理路径。

### 4.2 成本边界（必须守住）

- **token 膨胀**：每多一轮 = 一次失败输出注入 + 一次修复调用。
  预算上限（3 轮）保证单实例成本上限 ≈ 当前 ×2-3，仍在可接受范围
  （当前 < ¥0.1/实例，flash）。
- **死循环风险**：`verification_max_rounds` 硬上限 + `max_steps` 双闸门，
  fail-closed 保证不无限重试。
- **误报风险**：只有「有写操作 + 有失败测试 + 无成功测试」才进循环，
  纯读任务/无失败测试任务零成本（沿用 v0.8.2 条件）。

## 5. 实验设计（唯一变量原则）

沿用 v0.8.2 评测纪律（串行、同模型同参数唯一变量、成功复用失败重跑）：

1. **A 组：多轮验证循环**（框架侧唯一变量）
   - 基线：v0.8.2 配置（`verification_max_rounds=1`）
   - 实验：`verification_max_rounds=3`
   - 模型固定：flash 同档位；seed 同 20260729；`--max-steps 10`
2. **B 组：flash max 思考档**（模型侧唯一变量）
   - 基线：A 组基线（flash 未设档）
   - 实验：flash `reasoning_effort=max`，框架配置不变
3. **C 组：联合**（两杠杆叠加）
   - 预期：A、B 各自增益之和（若正交）
4. **判定标准**：instance-level resolved 数提升 ≥ 2（≈ +6.7pp 量级）
   才值得合入；否则回退并记录原因。

### 5.1 实施步骤

1. `_ensure_verification_loop` 循环化 + `verification_max_rounds` 配置项
2. 单测：补「补救后仍失败 → 第二轮补救」「成功 → 立即退出」
   「预算耗尽 → fail-closed」三个用例
3. 门禁：pytest（2110+）+ ruff + compileall + 本地安装验证
4. 5 引擎 × 30 实例串行评测（同 v0.8.2 流程），官方 harness grading
5. 结果落盘 `evals/results/`，A/B/C 三组对比入库
6. 通过则 bump 0.8.2 → 0.9.0，双远端 + release + CI

---

## 6. 风险与回退

| 风险 | 应对 |
|------|------|
| 多轮不提升（硬实例修不动） | 回退 `verification_max_rounds=1`，保留配置项，记录失败模式 |
| max 档成本超限 | 只对评测档开，默认配置不动；或用 high 档替代 |
| 轮间重复注入相同失败 | 失败输出去重（相同摘要不重复注入） |
| 与 mid-task steering 冲突 | 循环内不消费 steering（补救步骤是框架注入，非用户指令） |

---

## 7. 一句话结论

**v0.9 = 把已验证有效的「测试反馈修复」从 1 轮变成预算内多轮（框架侧），
叠加 flash max 思考档（模型侧），两个正交杠杆联合冲击 45-50%。**
若多轮增益不达阈值，保留配置项回退，不破坏 v0.8.2 已实证的 40.0%。
